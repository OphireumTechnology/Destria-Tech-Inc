# DESTRIA TECH INC — Engineering Repair & Hardening Walkthrough (`DTI-MASTER-REPAIR-001`)

# Security Summary

During this master audit and hardening pass across the DESTRIA TECH INC platform, we audited the authentication flow, Front Desk persistence layer, public static assets, Gemini AI runtime integration, consultation calendar sync, and CI/CD pipelines, and closed the following security gaps:

- **Removed sensitive internal prompt files from public static hosting:** Found and deleted 8 internal AI Studio text dumps (`Paste_*`) inside `public/assets/aistudio/` that would otherwise have been published to `https://destriatech.com/assets/aistudio/`, and added permanent guardrails in `scripts/lint-codebase.mjs`, `scripts/verify-clean-routing.mjs`, and GitHub Actions workflows so internal `Paste_*` files can never be shipped again.
- **Moved Admin authentication off browser web storage to HttpOnly cookies with CSRF protection and server-side logout revocation:** Removed all `sessionStorage` storage of admin bearer tokens (`opm_admin_token`) across `AdminPortalApp.tsx`, `AdminFrontDeskConsole.tsx`, and `EnterpriseModal.tsx`. Login now sets an `HttpOnly` session cookie (`dti_admin_session`), cookie-authenticated state-changing requests require the `X-Requested-With` header (blocking cross-site forged mutations with HTTP `403`), and `POST /api/admin/auth/logout` immediately revokes the session token ID (`jti`) server-side while clearing the cookie.
- **Enforced fail-closed durable persistence for AI Front Desk records in production:** Added additive SQL migration `008_ai_frontdesk_durability_hardening.sql` (with Row-Level Security enabled) and a Supabase write-through persistence adapter (`src/server/frontDeskRepository.ts`) so sessions, single-use confirmation tokens, submitted inquiries, reviews, escalations, quality logs, and managed knowledge documents survive restarts and fail closed with HTTP `503 DATABASE_UNAVAILABLE` if durable storage is missing in production.
- **Prevented API key leakage in Gemini error diagnostics and enforced HTTPS/WSS URL safety:** Added `classifyGeminiProviderError()` in `src/server/aiRuntimeConfig.ts` to categorize provider errors and redact any `AIzaSy...` keys or `Bearer` tokens before logging, and hardened `src/lib/apiClient.ts` to strip embedded URL credentials, prevent `/api/api` duplication, upgrade HTTP to HTTPS/WSS on secure pages, and reject `localhost` API targets baked into public builds.
- **Preserved prior security controls:** Maintained trusted-proxy rate-limiting (`req.ip`), single-use session-bound AI confirmation tokens, JSON-LD `<` (`\u003c`) escaping, strict Client Portal email ownership isolation, and server-only secret isolation.

## PoC Verification

Every security repair was verified with automated Proof-of-Concept regression tests in `tests/master-bulk-repair-dti001.test.ts` and `tests/security-hardening-regression.test.ts`:

1. **PoC 1 — Admin Cookie Auth, CSRF Mutation Block, and Server-Side Logout Revocation (`tests/master-bulk-repair-dti001.test.ts` Section 5):** Signed in via `POST /api/admin/auth/login`, verified `Set-Cookie` contains `dti_admin_session` with `HttpOnly`, confirmed `GET /api/admin/auth/session` succeeds via cookie alone, sent a mutating `POST /api/admin/frontdesk/quality` with the cookie but without `X-Requested-With` (rejected with HTTP `403 CSRF_CHECK_FAILED`), verified the same request succeeds (`201`) with `X-Requested-With: XMLHttpRequest`, logged out via `POST /api/admin/auth/logout` (`Max-Age=0`), and verified reusing the previously valid Bearer token immediately fails with HTTP `401`.
2. **PoC 2 — Fail-Closed Production Persistence & Concurrency Guards (`tests/master-bulk-repair-dti001.test.ts` Section 4):** Started the server in `productionStrictMode: true` with no durable Front Desk persistence and verified `GET /api/frontdesk/session/strict-prod-sess` fails closed with HTTP `503 DATABASE_UNAVAILABLE`. With durable persistence enabled, verified restart survival across fresh store instances, single-use confirmation token replay rejection, idempotent submission deduplication, stale `expectedVersion` rejection (`409`), and duplicate commercial approval rejection (`409`).
3. **PoC 3 — Gemini Error Redaction & Public Asset / Web Storage Hygiene (`tests/master-bulk-repair-dti001.test.ts` Sections 3 & 7):** Fed a simulated `401 API_KEY_INVALID` error containing an `AIzaSy...` key string into `classifyGeminiProviderError()` and verified it classifies as `INVALID_CREDENTIALS` (`retryable: false`) with zero key material remaining in `safeMessage`. Confirmed zero `Paste_*` files remain under `public/` and zero `sessionStorage`/`localStorage` admin token references exist anywhere in `src/`.
4. **PoC 4 — Rate-Limit IP Spoofing, Cross-Session Token Hijacking, and Live WebSocket Origin Blocking (`tests/security-hardening-regression.test.ts`):** Re-verified all prior PoCs remain green (`429` under forged `X-Forwarded-For` rotation, `400` on cross-session/replayed AI tool tokens, `403` on unauthorized WebSocket `Origin` upgrades).
